# Gelato System SaaS — ανάλυση και σχέδιο υλοποίησης

Ημερομηνία: 16/11/2026 · Στοίβα: Next.js 16.4.5, Prisma 7, PostgreSQL, React Native (Expo) για Android

## 1. Τι υπάρχει σήμερα (η εφαρμογή του πελάτη)

Η εφαρμογή `gelatosystem-app` είναι ήδη ώριμο προϊόν, όχι πρωτότυπο:

| Μέγεθος | Τιμή |
|---|---|
| Κώδικας TypeScript | ~251.000 γραμμές, 1.054 αρχεία |
| Βάση | 117 migrations, ~40.000 γραμμές SQL (κανόνες, triggers, συναρτήσεις) |
| Οθόνες | ~80 διαδρομές |
| Τεχνολογία | TanStack Start + Vite, Supabase (Postgres, σύνδεση χρηστών, αρχεία), Cloudflare Workers |
| Γλώσσες | Ελληνικά, Αγγλικά, Ιταλικά |

Ενότητες που καλύπτει: συνταγές με τεχνική ανάλυση, παραγωγή με lot, αποθήκη Α΄ υλών με μέσο σταθμικό κόστος, παραγγελίες υλών και MRP, προσφορές προμηθευτών, HACCP, ιχνηλασιμότητα, πελάτες χονδρικής, παραστατικά, διανομές, ψηφιακή βιτρίνα, προσωπικό και βάρδιες, οικονομικά (αγορές, πληρωμές, ταμείο, P&L, budget), κονσόλα πλατφόρμας και συνδρομές με χειροκίνητη πληρωμή.

**Τι δεν έχει:** πραγματική ηλεκτρονική τιμολόγηση (υπάρχει μόνο δοκιμαστικός πάροχος), ταμείο λιανικής (POS), πληρωμές με κάρτα, εφαρμογή Android, παραγγελιοληψία, εκτύπωση σε θερμικούς.

## 2. Τι χτίζουμε

Νέα εφαρμογή **από την αρχή**, με το ίδιο οπτικό, ως SaaS με μηνιαία χρέωση:

1. **Πυρήνας** — οι ενότητες του Gelato System, ξαναγραμμένες σε Next.js + Prisma.
2. **Ηλεκτρονική τιμολόγηση** — μέσω Viva (Viva Fiscalisation).
3. **Ταμείο λιανικής (POS)** — σε browser και σε Android, με πληρωμές Viva.
4. **Χρέωση** — ανά κατάστημα και ανά συσκευή τιμολόγησης.
5. **Αργότερα** — παραγγελιοληψία, εκτυπώσεις σε θερμικούς εκτυπωτές.

Από την παλιά εφαρμογή κρατάμε **μόνο το οπτικό και τη λογική των οθονών** (βλ. `DESIGN-SYSTEM.md`). Κώδικας και βάση είναι νέα.

## 3. Αρχιτεκτονική

```
Browser (ταμείο, διαχείριση) ──► Next.js 16 (Server Components + Server Actions) ──► PostgreSQL (Prisma)
Android (React Native)       ──► /api/pos/* (κλειδί συσκευής)                     ──┘
                                        │
                                        ├─► Viva Cloud Terminal API  (πληρωμή + σήμανση, ταμείο browser)
Android ──► Viva.com Terminal app (inter-app, ίδια συσκευή: πληρωμή + σήμανση)
```

- **Server Components παντού.** Οι σελίδες διαβάζουν τη βάση στον server. Οι ενέργειες (προσθήκη στο καλάθι, πληρωμή, νέα συσκευή) είναι Server Actions με φόρμες, χωρίς JavaScript στον browser. Μόνη εξαίρεση: η επισήμανση του ενεργού στοιχείου στο μενού, που εξαρτάται από το URL.
- **Πολλές επιχειρήσεις σε μία βάση.** Κάθε πίνακας έχει `orgId`. Κάθε ερώτημα φιλτράρει με αυτό, και κάθε ενέργεια ελέγχει ότι η εγγραφή ανήκει στην επιχείρηση του χρήστη.
- **Ποσά σε λεπτά** (ακέραιοι), ποτέ δεκαδικά.

### Πώς γίνεται μια πώληση

1. Ο ταμίας πατά προϊόντα· σχηματίζεται πρόχειρη πώληση στη βάση.
2. Στην πληρωμή, ο server κλειδώνει τη συσκευή, δίνει τον επόμενο αύξοντα αριθμό (ΑΑ) της σειράς της και φτιάχνει το `fiscalisationData`.
3. Το αίτημα πηγαίνει στο τερματικό Viva. Η Viva χρεώνει την κάρτα, υπογράφει την απόδειξη και τη διαβιβάζει στο myDATA.
4. Με επιτυχία, η πώληση κλείνει και ο ΑΑ «καίγεται». Με αποτυχία, η πώληση γυρίζει σε πρόχειρο και ο ΑΑ μένει ελεύθερος — έτσι **δεν δημιουργούνται κενά στην αρίθμηση**.

Κάθε συσκευή έχει **δική της σειρά** παραστατικών, ώστε δύο ταμεία να μη συγκρούονται ποτέ στον ίδιο αριθμό.

## 4. Viva: τι επιβεβαιώθηκε από την επίσημη τεκμηρίωση

| Θέμα | Τι ισχύει |
|---|---|
| Τιμολόγηση | Το Viva Fiscalisation υπογράφει και διαβιβάζει στο myDATA. Εμείς προσθέτουμε ένα αντικείμενο `fiscalisationData` στο αίτημα πώλησης· **δεν** στέλνουμε ξεχωριστά παραμέτρους ΑΑΔΕ. |
| Κανάλια | Cloud Terminal API (ταμείο σε browser), inter-app (Android, ίδια συσκευή), τοπικό API. Ίδιο `fiscalisationData` σε όλα. |
| Μετρητά | Περνούν **και αυτά από το τερματικό** (ως «ενδιάμεσος»), με τύπο πληρωμής «μετρητά». Χωρίς τερματικό Viva δεν εκδίδεται απόδειξη. |
| Αρίθμηση | Σειρά και ΑΑ τα κρατά **το δικό μας σύστημα**, αυστηρά αύξοντα, χωρίς κενά. |
| Πιστωτικά | Αναφέρονται στο αρχικό παραστατικό με το `cbReceiptReference` του (όχι με ΜΑΡΚ). |
| Τύποι παραστατικών | 11.1 ΑΛΠ, 11.2 ΑΠΥ, 1.1 τιμολόγιο, 5.1/5.2 πιστωτικά, 11.4, 8.6 δελτίο παραγγελίας, 9.3 δελτίο αποστολής κ.ά. |
| Λογαριασμός ISV | Ένας δικός μας λογαριασμός ISV εξυπηρετεί όλους τους εμπόρους (`isvDetails.terminalMerchantId`). |

**Περιορισμοί που επηρεάζουν το σχέδιο:**

- **Επιστροφές:** η επιστροφή με σήμανση **δεν** υποστηρίζεται με τα κλειδιά ISV· θέλει τα κλειδιά του ίδιου του εμπόρου. Άρα κάθε πελάτης μας πρέπει να μας δώσει και δικά του κλειδιά Viva (αποθήκευση κρυπτογραφημένη).
- **Ειδοποιήσεις αποτυχίας:** η Viva δεν στέλνει ακόμα webhook όταν αποτύχει η διαβίβαση· πρέπει να ρωτάμε εμείς.
- **Συσκευές:** η τεκμηρίωση γράφει ότι το fiscalisation διατίθεται «αυτή τη στιγμή μόνο σε SoftPOS για Android». Πρέπει να επιβεβαιωθεί με τη Viva ποια τερματικά το υποστηρίζουν.
- **Χωρίς σύνδεση:** το Cloud Terminal API δεν υποστηρίζει πληρωμές εκτός σύνδεσης· το inter-app και το τοπικό API τις υποστηρίζουν.
- Τα δείγματα της Viva είναι ενδεικτικά: **η τελική αντιστοίχιση ΦΠΑ και τύπων παραστατικών θέλει έλεγχο από λογιστή.**

Πηγές: [Viva Fiscalisation για ISV](https://developer.viva.com/viva-fiscalisation/fiscalisation-isv/), [βασικές έννοιες](https://developer.viva.com/viva-fiscalisation/core/), [Ελλάδα — συχνές ερωτήσεις](https://developer.viva.com/viva-fiscalisation/greece/faq/), [Ελλάδα — δείγματα](https://developer.viva.com/viva-fiscalisation/greece/samples/), [Cloud Terminal API](https://developer.viva.com/apis-for-point-of-sale/card-terminals-devices/rest-api/), [Android inter-app sale](https://developer.viva.com/apis-for-point-of-sale/card-terminal-apps/android-app/sale/).

## 5. Χρέωση συνδρομής

Μηνιαία χρέωση = **καταστήματα × τιμή καταστήματος + ενεργές συσκευές τιμολόγησης × τιμή συσκευής**.

- Οι τιμές ορίζονται σε ένα σημείο: `web/lib/pricing.ts`. **Οι σημερινές (59 € / κατάστημα, 15 € / συσκευή) είναι προσωρινές.**
- Μια συσκευή που απενεργοποιείται παύει να χρεώνεται.
- Κάθε μήνα αποθηκεύεται «φωτογραφία» του πλήθους (πίνακας `SubscriptionCharge`), ώστε ο λογαριασμός να μην αλλάζει εκ των υστέρων.
- Η είσπραξη της συνδρομής (αυτόματη χρέωση κάρτας μέσω Viva) είναι επόμενο βήμα.

## 10. Κονσόλα συνδρομητών, ρόλοι και πιστοποίηση συσκευών (προστέθηκε 16/11/2026)

**Κονσόλα πλατφόρμας** (`/platform`, μόνο για διαχειριστή πλατφόρμας):

- Λίστα επιχειρήσεων με κατάσταση συνδρομής, μηνιαίο ποσό και πόσα βήματα αρχικοποίησης λείπουν.
- Νέα επιχείρηση: δημιουργεί μαζί έδρα, κεντρική αποθήκη, πρώτο ταμείο (σειρά A1) και δοκιμαστική συνδρομή.
- Ανά επιχείρηση: συνδρομή και χρεώσεις, κωδικός εμπόρου Viva, υποκαταστήματα, αποθήκες, εκτυπωτές, ταμεία, χρήστες.
- Κατάσταση λογαριασμού Viva ISV και δοκιμή των κλειδιών. Τα κλειδιά ISV μένουν στο `.env` του server, δεν πληκτρολογούνται σε οθόνη.

**Ρόλοι:**

| Ρόλος | Βλέπει |
|---|---|
| Διαχειριστής πλατφόρμας | Μόνο την κονσόλα συνδρομητών· δεν ανήκει σε επιχείρηση |
| Ιδιοκτήτης | Όλα της επιχείρησής του, και τη συνδρομή |
| Υπεύθυνος | Όλα εκτός συνδρομής |
| Ταμίας | Μόνο ταμείο και αποδείξεις |

Ένας χρήστης μπορεί να περιοριστεί σε ένα κατάστημα. Σύνδεση με email και κωδικό (scrypt), συνεδρία σε httpOnly cookie, κλείδωμα 15 λεπτών μετά από 5 λάθος κωδικούς. Ο έλεγχος ρόλου γίνεται σε κάθε σελίδα και σε κάθε ενέργεια, όχι μόνο στο μενού.

**Πιστοποίηση συσκευών Android:**

1. Στην κονσόλα, στο ταμείο τύπου Android, «Κωδικός σύζευξης»: 8 χαρακτήρες, ισχύει 15 λεπτά, για μία χρήση.
2. Ο τεχνικός τον γράφει στην εφαρμογή· η συσκευή παίρνει μόνιμο κλειδί, που φυλάσσεται στο ασφαλές αποθετήριό της. Στη βάση μένει μόνο το sha256 του.
3. «Ανάκληση» ακυρώνει το κλειδί αμέσως (χαμένη ή κλεμμένη συσκευή).

**MAC και Tailscale:** κάθε ταμείο έχει πεδίο MAC (καταγραφή υλικού) και διεύθυνση Tailscale (100.x.y.z). Όταν οριστεί διεύθυνση Tailscale, η συσκευή γίνεται δεκτή **μόνο** από αυτήν, και στη σύζευξη και σε κάθε κλήση. Ο έλεγχος λειτουργεί μόνο με `TRUST_PROXY=1`, δηλαδή όταν ο server δέχεται κίνηση αποκλειστικά μέσα από proxy που γράφει ο ίδιος τη διεύθυνση προέλευσης (π.χ. `tailscale serve`)· αλλιώς μια τέτοια συσκευή απορρίπτεται. Η MAC δεν ελέγχεται αυτόματα: το Android δεν δίνει την πραγματική MAC σε εφαρμογές.

## 11. Ρυθμίσεις υπερδιαχειριστή, Mailgun και email (προστέθηκε 16/11/2026)

- **Ρυθμίσεις πλατφόρμας** (`/platform/settings`): όνομα πλατφόρμας, βασικός τομέας, email υποστήριξης, κατάσταση Mailgun με δοκιμαστική αποστολή, προεπισκόπηση όλων των email και ιστορικό αποστολών.
- **Mailgun:** ένα επαληθευμένο domain για όλη την πλατφόρμα (κλειδιά στο `.env`: `MAILGUN_API_KEY`, `MAILGUN_DOMAIN`, `MAILGUN_REGION`). Κάθε πελάτης στέλνει ως `υποτομέας@domain`, με όνομα «Επωνυμία μέσω Gelato System» και Reply-To το δικό του email. Χωριστό domain ανά πελάτη δεν χρειάζεται DNS από τον πελάτη· αν ζητηθεί αργότερα, αλλάζει μόνο το `lib/mail/send.ts`.
- **Ανά πελάτη:** υποτομέας (μοναδικός), email επικοινωνίας, όνομα αποστολέα. Ο υποτομέας δίνει και τη διεύθυνση `υποτομέας.βασικός-τομέας` που μπαίνει στους συνδέσμους των email.
- **Email:** ανάκτηση κωδικού, πρόσκληση χρήστη, νέα επιχείρηση, έκδοση χρέωσης, επιβεβαίωση πληρωμής, λήξη δοκιμής σε λίγες ημέρες, λήξη συνδρομής, δοκιμαστικό. Ένα κοινό πρότυπο (`lib/mail/templates.ts`), HTML και απλό κείμενο.
- **Ανάκτηση κωδικού:** «Ξέχασα τον κωδικό» → σύνδεσμος μίας χρήσης (1 ώρα)· με την αλλαγή αποσυνδέονται όλες οι συσκευές του χρήστη. Η πρόσκληση νέου χρήστη χρησιμοποιεί τον ίδιο μηχανισμό (72 ώρες).
- **Προγραμματισμένα:** `POST /api/cron/subscriptions` με `Authorization: Bearer $CRON_SECRET`, μία φορά την ημέρα: υπενθύμιση 3 ημέρες πριν λήξει η δοκιμή, και σήμανση «ληξιπρόθεσμη» με ειδοποίηση όταν λήξει η συνδρομή. Κάθε τέτοιο email φεύγει μία φορά ανά περίοδο.
- **Επανάληψη διαβιβάσεων:** `POST /api/cron/fiscal` (ίδιο `CRON_SECRET`) κάθε 5 λεπτά. Ξαναστέλνει τα 8.6 και τα παραστατικά χονδρικής που απέτυχαν λόγω σύνδεσης, με αναμονή 1, 2, 4 … λεπτά έως 6 ώρες και έως 20 προσπάθειες, με το ίδιο reference, άρα το ίδιο MARK. Ό,τι απέρριψε η ΑΑΔΕ δεν ξαναστέλνεται: φαίνεται στο «Διαβιβάσεις myDATA» ως «Θέλουν διόρθωση». Κάθε αλλαγή κατάστασης γράφεται από trigger στο `FiscalAttempt`, μόνο με προσθήκη, και εξάγεται σε CSV για έλεγχο.
- **Εκκρεμεί:** η δρομολόγηση ανά υποτομέα (ο χρήστης της aurora να μπαίνει μόνο από το aurora.…) δεν ελέγχεται ακόμα· ο υποτομέας χρησιμοποιείται προς το παρόν μόνο στους συνδέσμους και στον αποστολέα.

## 12. RBAC, πληρωμή συνδρομών, πίνακες, PWA (προστέθηκε 16/11/2026)

**Ρόλοι πλατφόρμας** (σταθεροί, `lib/permissions.ts`): Super Admin (όλα), Manager (συνδρομητές, συνδρομές, αρχικοποίηση), Υπάλληλος εφαρμογής (αρχικοποίηση, χωρίς χρεώσεις), Υπάλληλος υποστήριξης (προβολή και βοήθεια χρηστών). Διαχείριση προσωπικού στις Ρυθμίσεις· πάντα μένει τουλάχιστον ένας Super Admin.

**Ρόλοι συνδρομητή** (δεδομένα ανά επιχείρηση): κάθε επιχείρηση ξεκινά με Επιχειρηματία (όλα, κλειδωμένος), Manager και Υπάλληλο, και φτιάχνει δικούς της ρόλους επιλέγοντας δικαιώματα. Σελίδα «Χρήστες & ρόλοι» (`/users`): πρόσκληση με email, αλλαγή ρόλου και καταστήματος, αφαίρεση πρόσβασης, ρόλοι με δικαιώματα. Κανόνες: κανείς δεν δίνει δικαίωμα που δεν έχει ο ίδιος, και πάντα μένει κάποιος που διαχειρίζεται χρήστες.

**Δικαιώματα σήμερα:** πίνακας ελέγχου, ταμείο, αποδείξεις, συσκευές, συνδρομή, χρήστες & ρόλοι. Κάθε νέα ενότητα του πυρήνα προσθέτει τα δικά της στον ίδιο κατάλογο.

**Πληρωμή συνδρομών:** οι χρεώσεις πληρώνονται με κάρτα στον λογαριασμό Viva της πλατφόρμας (Smart Checkout, κλειδιά `VIVA_PLATFORM_*`, διαφορετικά από του ISV). Ο συνδρομητής πατά «Πληρωμή με κάρτα» στη σελίδα «Συνδρομή», πληρώνει στη Viva και επιστρέφει στο `/billing/paid`, όπου η εφαρμογή ρωτά τη Viva και ταιριάζει κωδικό εντολής και ποσό πριν εξοφλήσει τη χρέωση. Το ποσό είναι η χρέωση + ΦΠΑ 24%. Εκκρεμεί το webhook της Viva για την περίπτωση που ο πελάτης δεν επιστρέψει στη σελίδα.

**Διεπαφή:** πλαϊνό μενού με ομάδες που ανοίγουν/κλείνουν και σύμπτυξη σε στήλη εικονιδίων· όλες οι φόρμες σε παράθυρα (modals)· κοινός πίνακας δεδομένων με αναζήτηση και σελιδοποίηση από τον server, αλλαγή πλάτους στηλών, επιλογή ορατών στηλών, μενού ανά γραμμή και αριθμούς στοιχισμένους δεξιά· τυπογραφία σε rem με βάση 11,5px (ετικέτες 10px)· η εφαρμογή εγκαθίσταται ως PWA, με σελίδα «εκτός σύνδεσης» (δεν κρατά δεδομένα επιχείρησης εκτός σύνδεσης).
