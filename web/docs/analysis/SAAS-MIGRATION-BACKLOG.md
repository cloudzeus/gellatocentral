# Μετάβαση παλιού Gelato System στο νέο SaaS — backlog

Ημερομηνία: 2026-11-22
Σκοπός: πλήρης λειτουργική κάλυψη της παλιάς εφαρμογής πάνω στο νέο multi-tenant μοντέλο, χωρίς απλή αντιγραφή της παλιάς αρχιτεκτονικής.

## 0. Πραγματική κατάσταση υλοποίησης — 2026-11-24

Η κύρια επιχειρησιακή αλυσίδα έχει μεταφερθεί στο νέο server-side, tenant-aware μοντέλο. Η παρακάτω καταγραφή διαχωρίζει τη λειτουργική υλοποίηση από εξωτερικές ολοκληρώσεις και production cutover· δεν σημαίνει ότι κάθε P1/P2 επέκταση έχει ολοκληρωθεί.

### Υλοποιημένοι και ελεγμένοι λειτουργικοί κορμοί

- **SaaS/RBAC:** ενιαία permissions, module access, tenant/store/warehouse scopes, audit και προστασία ευαίσθητων δεδομένων αμοιβών.
- **Απόθεμα:** υπολοίπα από append-only κινήσεις, παρτίδες/FEFO, λήξεις, low stock, ατομικές μεταφορές, απογραφές, παγωμένα snapshots, διορθώσεις και idempotent retries.
- **Αγορές:** παραγγελίες, παραλαβές/αναίρεση, σύνδεση με `PurchaseDoc`, MRP και RFQ με περιορισμένα δημόσια tokens.
- **Παραγωγή:** υποσυνταγές, αναδρομική ανάλυση, recipe snapshots, προγραμματισμός, ημερήσιο κλείσιμο, output correction, HACCP/holds, μηχανήματα και πρόβλεψη ζήτησης.
- **Χονδρική:** τιμοκατάλογοι, παραγγελίες, δρομολόγια/παραδόσεις, δελτία/τιμολόγια/πιστωτικά, εισπράξεις/allocations, B2B portal και χρονολόγιο πελάτη.
- **Προσωπικό/οικονομικά:** μητρώο, βάρδιες/άδειες, δημοσιεύσεις και προσωπικά links, payroll summary, λογαριασμοί/transfers, έξοδα, πληρωμές, cash close/reopen, budgets και εταιρικά στοιχεία.
- **Αναφορές/βιτρίνα:** scoped dashboard, πωλήσεις/COGS/P&L/VAT/aging/cash, αναφορές παραγωγής και δημόσια βιτρίνα με tokens και ανώνυμα view counts.
- **Μεταφορά:** canonical JSON, strict validation, dry-run, ατομικό/idempotent import για parties, items, lots και ιστορικά παραστατικά, reconciliation και ελεγχόμενο rollback μόνο των εγγραφών του run.
- **Δοκιμαστικά δεδομένα:** επαναλήψιμο `npm run demo:seed` μόνο με ρητή επιβεβαίωση και database name `gelato_agent_*`, χωρίς users/passwords/sessions ή φορολογική διαβίβαση.
- **Κεντρικό E2E:** `lib/business-e2e.integration.ts` καλύπτει PO → receipt/FEFO → subrecipe/day close/correction → transfer → count → wholesale/delivery/invoice/credit → payment → cash close → P&L, με δεύτερο tenant, scoped χρήστη και χειροκίνητα αναμενόμενα ποσά.

## 1. Αφετηρία και κανόνες

### Υπάρχων κορμός που επαναχρησιμοποιείται

- Multi-tenant `Organization`, `Store`, `Membership`, RBAC, πακέτα και συνδρομές.
- POS, αποδείξεις, συσκευές, Viva και βασική φορολογική υποδομή.
- `Party`/`Person` για πελάτες, προμηθευτές και λοιπούς συναλλασσομένους.
- `GenericItem`/`TradeItem`/`SupplierItem`, τιμές και τιμολόγια αγοράς.
- Συνταγές με τεχνική ανάλυση, βασικό κόστος και σύνδεση με προϊόν POS.
- `StockLot`, `StockMovement`, απλό κλείσιμο παραγωγής FEFO και ιχνηλασιμότητα.
- Αρχεία, email, GDPR, υποστήριξη και κονσόλα πλατφόρμας.

### Υποχρεωτικοί κανόνες κάθε εργασίας

1. Κάθε νέα επιχειρησιακή οντότητα έχει `orgId`· όταν η εργασία γίνεται ανά κατάστημα, και `storeId`.
2. Κάθε query, mutation, export, background job και public token ελέγχει tenant και κατάστημα/αποθήκη πρόσβασης.
3. Χρήματα σε λεπτά `Int`. Κόστη που χρειάζονται μεγαλύτερη ακρίβεια σε εκατοστά λεπτού, όπως στις συνταγές.
4. Ποσότητες στη βασική μονάδα του είδους. Καμία μετατροπή μάζας/όγκου/τεμαχίων χωρίς ρητό κανόνα.
5. Πολλαπλές εγγραφές σε μία `db.$transaction`. Κρίσιμες ροές με κλείδωμα/ελέγχους ταυτόχρονης εκτέλεσης και idempotency.
6. Νέα permissions στο `lib/permissions.ts`, σύνδεση με πακέτα στο `lib/modules.ts` και ελέγχους και σε UI και σε server.
7. Καμία εξάρτηση από browser για ευαίσθητες κλήσεις τρίτων. Δημόσιες σελίδες μόνο με ασφαλή, περιορισμένα tokens.
8. Κάθε φάση κλείνει με `npm test && npx tsc --noEmit`. Αν αλλάζει schema: migration, `npx prisma generate` και ξανά tests.

### Προτεραιότητες

- **P0 — κλειδί αλυσίδας:** απαραίτητο για αξιόπιστη καθημερινή λειτουργία.
- **P1 — πλήρης ισοτιμία:** βασική λειτουργία της παλιάς εφαρμογής, αλλά μπορεί να ακολουθήσει το P0.
- **P2 — επέκταση:** αυτοματισμοί, analytics και βελτιώσεις μετά τη σταθεροποίηση της κύριας ροής.

## 3. Ελάχιστο end-to-end MVP

Για πρώτη χρήσιμη επιχειρησιακή έκδοση πέρα από το POS, το ελάχιστο πακέτο είναι:

1. **SAAS-01 έως SAAS-04**.
2. **STK-01 έως STK-07**· το offline μπορεί να ακολουθήσει.
3. **PRC-01, PRC-02, PRC-04**.
4. **PRD-01 έως PRD-05**.
5. **HACCP-01**.
6. **WHL-01, WHL-02, WHL-05, WHL-06, WHL-07**.
7. **FIN-01, FIN-02, FIN-04**.
8. **MIG-01 έως MIG-06** για τους tenants που μεταφέρουν ιστορικό.

MRP/RFQ, B2B portal, πρόβλεψη 7 ημερών, προχωρημένο finance, budgets και vitrine analytics δεν μπλοκάρουν το πρώτο MVP, αρκεί να μην προπορευτούν των δεδομένων από τα οποία τροφοδοτούνται.

## 4. Κεντρικό integration test πριν από το cutover

Ένα φρέσκο test tenant πρέπει να περνά αυτόματα το σενάριο:

**προμηθευτής → παραγγελία → παραλαβή/τιμολόγιο → σταθμισμένο κόστος → συνταγή/υποσυνταγή → προγραμματισμός → παραγωγή/FEFO → μεταφορά → απογραφή/φύρα → παραγγελία χονδρικής → παράδοση → τιμολόγιο/myDATA → είσπραξη → κλείσιμο ταμείου → P&L**

Το ίδιο σενάριο επαναλαμβάνεται με δεύτερο tenant για απόδειξη ότι δεν διαρέει κανένα δεδομένο, και με χρήστες περιορισμένων ρόλων για RBAC/pay privacy.
