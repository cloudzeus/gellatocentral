# Γενικά είδη, συσκευασμένα είδη, προμηθευτές και τιμές αγοράς — ανάλυση & σχεδιασμός

Ημερομηνία: 2026-11-20
Κατάσταση: φάσεις 1–4 υλοποιημένες (μονάδες, κατάλογος, γέφυρα, τιμές/συμφωνίες, τιμολόγια αγοράς με σάρωση GS1,
έλεγχος συμφωνιών στο τιμολόγιο, OCR pay-per-use και λήψη από myDATA)· επόμενο η φάση 5 (συνταγές/απόθεμα, §10)

## 1. Στόχος

Ο συνδρομητής καταχωρεί **γενικά είδη** (τι καταναλώνει η συνταγή: «γάλα», «ζάχαρη», «φιστίκι Αιγίνης»)
με μονάδες μέτρησης, και μετά συσχετίζει **συσκευασμένα είδη** (τι αγοράζει: «Γάλα ΔΕΛΤΑ 1,5% 1L»)
από **πολλούς προμηθευτές**, με **κωδικό προμηθευτή / barcode / EAN**, **συσκευασία** και **τιμή**.
Πάνω σε αυτό κουμπώνουν:

- τιμολόγια αγοράς (η γραμμή του τιμολογίου αναγνωρίζει το είδος και ενημερώνει τιμή & απόθεμα),
- **ειδικές συμφωνίες**: τιμή ανά προμηθευτή + είδος, με όρο ποσότητας ή χρονικό διάστημα ή και τα δύο,
- μελλοντικά: συνταγές (υλικά → γενικά είδη), κόστος συνταγής, αποθέματα ανά είδος.

## 2. Τρέχουσα κατάσταση (γιατί χρειάζεται νέα σχεδίαση)

- Το `Product` είναι κατάλογος **πώλησης** ταμείου: μία τιμή με ΦΠΑ, χωρίς κωδικό, χωρίς μονάδα, χωρίς σχέση με προμηθευτή ή απόθεμα. Δεν αλλάζει ρόλο — παραμένει «τι πουλάω στον πελάτη».
- Το `StockMovement` δεν αναφέρεται σε είδος (μόνο `documentId`/`lineId` κείμενο).
- Υπάρχει ήδη κοινή λίστα `RefItem` με `list = "unit"` («Μονάδες μέτρησης — για είδη, συνταγές και αποθήκη»), οπότε η σύλληψη ήταν προβλεμμένη· η λίστα όμως είναι απλό λεξικό, χωρίς διαστάσεις και μετατροπές.
- Το `Party` με ρόλο `supplier`, το `DocumentType` και το `FiscalDocument` καλύπτουν τη φορολογική πλευρά του τιμολογίου αγοράς.

## 3. Οι δύο έννοιες-κλειδιά

| Έννοια | Τι είναι | Πού ζει | Παράδειγμα |
|-|-|-|-|
| **Γενικό είδος** (`GenericItem`) | Η «ουσία» που καταναλώνει η συνταγή και μετράει η αποθήκη | Ανά επιχείρηση (`orgId`) | «Γάλα αγελάδος», «Ζάχαρη» |
| **Εμπορικό είδος** (`TradeItem`) | Η συγκεκριμένη συσκευασία που αγοράζει κανείς, με brand, κατασκευαστή, EAN, φωτογραφία | **Κεντρικά στην πλατφόρμα** (χωρίς `orgId`) | «Γάλα ΔΕΛΤΑ 1,5% χαρτοκιβώτιο 1L», EAN 520… |

Η διαχωριστική γραμμή: το γενικό είδος απαντά «**τι χρειάζομαι**», το εμπορικό «**τι ακριβώς αγόρασα**».
Ο συνδρομητής δεν ξανακαταχωρεί ποτέ τα εμπορικά είδη — τα βρίσκει στον κεντρικό κατάλογο με EAN/όνομα
και απλώς τα «υιοθετεί»: τα δένει με το δικό του γενικό είδος.

Συνέπεια: η αποθήκη και οι συνταγές μιλούν πάντα σε **γενικά είδη και βασικές μονάδες**·
οι αγορές μιλούν σε **εμπορικά είδη και συσκευασίες**· η γέφυρα είναι ο πίνακας αντιστοίχισης (§5).

## 4. Μονάδες μέτρησης

Η λίστα `RefItem("unit")` δεν φτάνει: χρειαζόμαστε διάσταση και μετατροπή. Νέο κοινό μοντέο πλατφόρμας
(χωρίς `orgId`, seeded, στη λογική του `VatRate`):

```prisma
// Μονάδα μέτρησης, κοινή για όλους (seeded). Η μετατροπή γίνεται μόνο μέσα στην ίδια διάσταση.
model Unit {
  id        String  @id @default(cuid())
  code      String  @unique // "kg", "g", "l", "ml", "pcs"…
  nameEL    String
  dimension String // mass | volume | count — αλλιώτικες διαστάσεις δεν μετατρέπονται μεταξύ τους
  toBase    Int // πόσες βασικές μονάδες είναι η μία· π.χ. g: 1000 (1 g = 1000 mg), kg: 1_000_000
  active    Boolean @default(true)
}
```

Σχεδιαστικές αποφάσεις:

- **Ποσότητες σε Int** (παντού ακέραιοι, όπως τα χρήματα σε λεπτά): αποθηκεύονται κατευθείαν στη
  βασική μονάδα (mg / ml / τεμάχιο). Η εναλλακτική «χιλιοστά της βασικής» απορρίφθηκε: το σακί
  25 kg θα ήταν 2,5·10¹⁰ μονάδες και ξεχειλώνει το Int32. Σε mg/ml χωράει έως ~2 τόνους ανά κίνηση.
  Το υπάρχον `StockMovement.quantity Int` συνεχίζει έτσι χωρίς τύπο Float.
- **Η συσκευασία ΔΕΝ είναι μονάδα**: «κιβώτιο 12×1L» είναι εμπορικό είδος με περιεχόμενο 12 L,
  όχι μονάδα «κιβώτιο». Στο `TradeItem` κρατάμε `contentQty` + `contentUnitId` (π.χ. 12_000 ml).
- Καμία μετατροπή μεταξύ διαστάσεων (τεμάχια → kg) στο επίπεδο μονάδων· αν ποτέ χρειαστεί
  (π.χ. «1 αυγό = 55 g»), είναι ιδιότητα του **γενικού είδους**, όχι της μονάδας.

## 5. Κεντρικός κατάλογος εμπορικών ειδών

```prisma
// Κατασκευαστής/βιομηχανία (πλατφόρμας). Το brand μπορεί να είναι και ίδιο με τον κατασκευαστή.
model Manufacturer {
  id        String  @id @default(cuid())
  name      String  @unique // «ΦΑΓΕ», «ΔΕΛΤΑ»…
  brands    Brand[]
}

model Brand {
  id             String       @id @default(cuid())
  manufacturerId String
  name           String // «ΤΩΝ 150», «ΑΓΓΕΛΑΚΗΣ»…
  manufacturer   Manufacturer @relation(fields: [manufacturerId], references: [id])
  items          TradeItem[]

  @@unique([manufacturerId, name])
}

// Συσκευασμένο είδος εμπορίου. Κεντρικό: orgId κενό = κοινό της πλατφόρμας·
// orgId συμπληρωμένο = «ιδιωτικό» είδος συνδρομητή που δεν υπάρχει στον κεντρικό (π.χ. χύμα από μικρό παραγωγό).
model TradeItem {
  id             String        @id @default(cuid())
  orgId          String? // κενό = κεντρικός κατάλογος
  brandId        String?
  ean            String? // EAN-13/GTIN — μοναδικό στον κεντρικό κατάλογο
  name           String // «Γάλα φρέσκο 1,5% 1L»
  packaging      String? // περιγραφή συσκευασίας: «χαρτοκιβώτιο», «τεμαχίων 12»
  contentQty     Int // περιεχόμενο σε βασική μονάδα (§4): 1L → 1000 (ml), 25 kg → 25_000_000 (mg)
  contentUnitId  String // η μονάδα κατανάλωσης του περιεχομένου
  familyCode     String? // ομαδοποίηση ποικιλιών συσκευασίας ίδιου είδους («DELTA-GA-1.5»: 1L, 1,5L…) — απλό κείμενο, όχι ιεραρχία
  active         Boolean       @default(true)
  brand          Brand?        @relation(fields: [brandId], references: [id], onDelete: SetNull)
  contentUnit    Unit          @relation(fields: [contentUnitId], references: [id])
  supplierItems  SupplierItem[]
  adoptions      ItemMapping[]

  @@unique([orgId, ean])
  @@index([orgId, name])
}
```

- **Φωτογραφία**: μέσω του υπάρχοντος `StoredFile` με `refType = "tradeItem"` και `public = true`
  (CDN) — καμία νέα υποδομή αρχείων.
- **EAN**: μοναδικό μόνο στον κεντρικό κατάλογο (`@@unique([orgId, ean])` με `orgId = null` χρειάζεται
  προσοχή στο Postgres/NULL — εναλλακτικά partial unique index μέσω migration· σημείο υλοποίησης).
- Ο κεντρικός κατάλογος τρέφεται: (α) από την πλατφόρμα (seed/ένταξη), (β) **από αιτήματα συνδρομητών**:
  όταν κάποιος σκανάρει EAN που λείπει, το καταχωρεί ως «πρόχειρο κεντρικό» και η πλατφόρμα το εγκρίνει
  (μπαίνει στις ροές της υποστήριξης, όπως τα άρθρα KB). Έτσι η ποιότητα του κοινού καταλόγου
  δεν αφήνεται στο έλεος κάθε tenant.

## 6. Η γέφυρα: γενικό ↔ εμπορικό ↔ προμηθευτής

```prisma
// Γενικό είδος του συνδρομητή: αυτό που μπαίνει σε συνταγές και μετράει το απόθεμα.
model GenericItem {
  id         String   @id @default(cuid())
  orgId      String
  name       String
  baseUnitId String // η μονάδα ΚΑΤΑΝΑΛΩΣΗΣ (και αποθέματος): g, ml, τεμ
  vatRateId  String? // ΦΠΑ αγοράς, αν διαφέρει από το προεπιλεγμένο
  active     Boolean  @default(true)
  baseUnit   Unit     @relation(fields: [baseUnitId], references: [id])
  mappings   ItemMapping[]

  @@unique([orgId, name])
  @@index([orgId])
}

// «Σε εμένα, αυτό το εμπορικό είδος είναι αυτό το γενικό». Ανά συνδρομητή·
// πολλά εμπορικά (ΔΕΛΤΑ, ΦΑΓΕ, ιδιωτικό χύμα) δένουν στο ίδιο γενικό.
model ItemMapping {
  id            String      @id @default(cuid())
  orgId         String
  genericItemId String
  tradeItemId   String
  genericItem   GenericItem @relation(fields: [genericItemId], references: [id], onDelete: Cascade)
  tradeItem     TradeItem   @relation(fields: [tradeItemId], references: [id], onDelete: Cascade)

  @@unique([orgId, tradeItemId])
  @@index([genericItemId])
}

// Το είδος ΟΠΩΣ το πουλάει συγκεκριμένος προμηθευτής στον συνδρομητή:
// δικός του κωδικός, δική του συσκευασία πώλησης, τρέχουσα τιμή (από την τελευταία SupplierItemPrice).
model SupplierItem {
  id             String   @id @default(cuid())
  orgId          String
  supplierId     String // Party με ρόλο supplier
  tradeItemId    String
  supplierCode   String? // ο κωδικός είδους στα παραστατικά του προμηθευτή
  packQty        Int      @default(1) // ελάχιστη πώληση: πόσα TradeItem ανά «συσκευασία παραγγελίας» (π.χ. κιβώτιο 12)
  barcode        String? // αν ο προμηθευτής στέλνει δικό του barcode (συνήθως = EAN του TradeItem)
  active         Boolean  @default(true)
  supplier       Party    @relation(fields: [supplierId], references: [id])
  tradeItem      TradeItem @relation(fields: [tradeItemId], references: [id])
  prices         SupplierItemPrice[]

  @@unique([orgId, supplierId, supplierCode])
  @@index([orgId, tradeItemId])
}
```

Σημειώσεις:

- **Πολλοί προμηθευτές για το ΙΔΙΟ εμπορικό είδος**: είναι ο βασικός λόγος ύπαρξης του `SupplierItem`.
  Το «Γάλα ΔΕΛΤΑ 1L» (ένα `TradeItem`, ένα EAN) παίρνει ένα `SupplierItem` ανά προμηθευτή — ο καθένας με
  δικό του `supplierCode`, `packQty` και δικό του ιστορικό τιμών. Το `@@unique` είναι επί
  `(orgId, supplierId, supplierCode)`, όχι επί του `tradeItemId`, ακριβώς γι' αυτό.
  Μπόνους: η σύγκριση «ποιος το δίνει φθηνότερα» είναι ένα query πάνω σε όλα τα `SupplierItem`
  του ίδιου `tradeItemId` (κανονικοποιημένα ανά βασική μονάδα: `priceCents / contentQty`).
- Η σχέση προμηθευτή είναι **ανά συνδρομητή** (`orgId`): ο ίδιος προμηθευτής μπορεί να δίνει
  διαφορετικό κωδικό και τιμή σε κάθε πελάτη.
- `@@unique([orgId, supplierId, supplierCode])` επιτρέπει στο τιμολόγιο αγοράς να βρει το είδος
  με ένα lookup: (orgId, supplier, κωδικός γραμμής). Το EAN είναι η δεύτερη πηγή αντιστοίχισης.
- `packQty` λύνει το κλασικό «πουλάει μόνο κιβώτιο» χωρίς να γίνει η συσκευασία μονάδα μέτρησης.

## 7. Τιμές και ειδικές συμφωνίες

Ένας πίνακας τιμών με **προϋποθέσεις** καλύπτει και τον τιμοκατάλογο και τις συμφωνίες — δεν χρειάζονται δύο μοντέλα:

```prisma
// Τιμή αγοράς με όρους. Η «κανονική» τιμή είναι η γραμμή χωρίς όρους·
// η ειδική συμφωνία είναι γραμμή με minPackQty ή/και διάστημα ισχύος.
// Μόνο προσθήκες (ιστορικό)· η τρέχουσα είναι η πιο πρόσφατη που ισχύει.
model SupplierItemPrice {
  id             String       @id @default(cuid())
  supplierItemId String
  priceCents     Int // τιμή ανά TradeItem (όχι ανά packQty), προ ΦΠΑ, σε λεπτά
  minPackQty     Int? // ελάχιστη ποσότητα συσκευασιών παραγγελίας για να ισχύσει
  validFrom      DateTime     @default(now())
  validTo        DateTime?
  note           String? // «Συμφωνία έκθεσης 2026», «προσφορά Νοεμβρίου»
  createdByName  String
  createdAt      DateTime     @default(now())
  supplierItem   SupplierItem @relation(fields: [supplierItemId], references: [id], onDelete: Cascade)

  @@index([supplierItemId, validFrom])
}
```

**Κανόνας ανάλυσης τιμής** (για ποσότητα `q` συσκευασιών, ημερομηνία `d`):

1. Πάρε τις γραμμές του `SupplierItem` με `validFrom ≤ d ≤ validTo (ή κενό)` και `minPackQty ≤ q (ή κενό)`.
2. Από αυτές κερδίζει η πιο «συγκεκριμένη» (με minPackQty και διάστημα > με ένα από τα δύο > χωρίς όρους)·
   σε ισοπαλία η νεότερη `validFrom`.
3. Αν τίποτα δεν ισχύει, fallback στην τελευταία άνευ όρων (ή «χωρίς τιμή» — αναγκαστική συμπλήρωση).

Έτσι η «ειδική συμφωνία για ποσότητα ΚΑΙ ημερομηνία» είναι απλώς γραμμή με και τα δύο πεδία,
και το ιστορικό τιμών βγαίνει δωρεάν (μόνο προσθήκες, όπως `Consent`/`GdprEvent`).

**Απόφαση**: όλες οι τιμές αγοράς καταχωρούνται και αποθηκεύονται **πάντα χωρίς ΦΠΑ**
(η οθόνη δείχνει δευτερευόντως και το τελικό ποσό με ΦΠΑ, από τον `vatRateId` του γενικού είδους).

## 8. Barcode scanning στην καταχώριση

Η σάρωση δεν είναι ξεχωριστή οθόνη — είναι **τρόπος εισαγωγής** που μπαίνει παντού όπου ψάχνουμε είδος.
Στόχος: ο χρήστης σπανίως πληκτρολογεί EAN.

Σημεία ένταξης:

1. **Υιοθεσία εμπορικού είδους** (§5): σάρωση EAN → αναζήτηση στον κεντρικό κατάλογο.
   Βρέθηκε → ένα κλικ δέσιμο με γενικό είδος. Δεν βρέθηκε → δημιουργία «πρόχειρου κεντρικού» TradeItem
   με το EAN ήδη συμπληρωμένο (ο χρήστης βάζει όνομα/brand/φωτογραφία από το κινητό), το οποίο πάει
   προς έγκριση στην πλατφόρμα.
2. **Τιμολόγιο αγοράς** (§9): σάρωση της συσκευασίας κατά την παραλαβή δημιουργεί/αντιστοιχεί τη γραμμή
   χωρίς να χρειάζεται ο κωδικός του προμηθευτή (το EAN είναι η δεύτερη πηγή αντιστοίχισης και γίνεται πρώτη).
3. **Σύνδεση προμηθευτή**: στο `SupplierItem`, αν ο προμηθευτής στέλνει δικό του barcode, σαρώνεται στο πεδίο
   `barcode` — διαφορετικά υιοθετείται αυτόματα το EAN του TradeItem.

Τεχνικές αποφάσεις:

- **Web (ταμείο/κονσόλα)**: Barcode Detection API με fallback σε πεδίο «πληκτρολόγηση από scanner»
  (οι USB/Bluetooth scanners είναι HID πληκτρολόγια· το πεδίο ακούει ακολουθία που κλείνει με Enter).
  Καμία εξάρτηση από βαρύ native SDK.
- **Android POS**: ενσωμάτωση στο υπάρχον inter-app κανάλι — σάρωση με την κάμερα της συσκευής.
- **Μορφές**: EAN-13/GTIN ως βάση· το parsing κρατά μόνο τα ψηφία (κανονικοποίηση, έλεγχος check digit).
  **GS1-128/DataMatrix με AI(01) GTIN, AI(10) παρτίδα, AI(17) λήξη: από την πρώτη υλοποίηση** —
  η ιχνηλασιμότητα (παρτίδες) είναι απαίτηση τώρα, όχι μελλοντική (§10). Ο parser είναι ένα κοινό
  lib (`lib/gs1.ts`) που επιστρέφει { gtin, batch, expiry }· τα πεδία γεμίζουν τη γραμμή αγοράς.
- Ενιαίο client util (`components/barcode-field`) ώστε κάθε φόρμα να παίρνει σάρωση με μία ιδιότητα —
  η ίδια θα ξαναχρησιμοποιηθεί αργότερα στο POS και στην απογραφή αποθήκης.

## 9. Τιμολόγιο αγοράς και αντιστοίχιση γραμμών

Ροή:

1. Έρχεται/καταχωρείται τιμολόγιο αγοράς από προμηθευτή (`FiscalDocument` με `partyId` = προμηθευτής,
   `docType` 1.x/6.x). Χρειάζεται νέο `PurchaseLine` μοντέλο (το `FiscalDocument` σήμερα δεν έχει γραμμές — μόνο POS `SaleLine`).
2. Κάθε γραμμή κρατά: κωδικό προμηθευτή, περιγραφή, ποσότητα, τιμή, EAN (αν υπάρχει).
3. **Αντιστοίχιση** με σειρά προτεραιότητας:
   α. `supplierCode` → `SupplierItem` (έτοιμο, μαθαίνει με κάθε επιβεβαίωση),
   β. EAN → `TradeItem` → (αν λείπει `SupplierItem`) δημιουργείται με ένα κλικ,
   γ. ομοιότητα περιγραφής (fuzzy) → πρόταση, ο χρήστης επιβεβαιώνει,
   δ. ασύμβατο → ο χρήστης το δένει χειροκίνητα ή δημιουργεί νέο γενικό/εμπορικό είδος.
4. Κάθε **επιβεβαίωση** γράφει/ενημερώνει το `SupplierItem.supplierCode`, ώστε η επόμενη φορά να είναι αυτόματη.
5. Η αποδοχή του τιμολογίου: γράφει `StockMovement` ανά γενικό είδος (μέσω `ItemMapping`, ποσότητα σε βασική μονάδα)
   και προσθέτει `SupplierItemPrice` αν η τιμή άλλαξε — όλα μέσα σε `db.$transaction`.

```prisma
model PurchaseLine {
  id             String    @id @default(cuid())
  orgId          String
  documentId     String // FiscalDocument
  supplierCode   String?
  ean            String?
  description    String // όπως ήρθε από τον προμηθευτή
  quantity       Int // σε μονάδα παραστατικού
  unitPriceCents Int
  // Ιχνηλασιμότητα: από GS1 σάρωση ή χειροκίνητα· τροφοδοτούν το StockLot της παραλαβής
  batchNumber    String?
  expiresAt      DateTime?
  // Έλεγχος παραλαβής HACCP (Καν. 852/2004 αρ. 5, οδηγοί ΕΦΕΤ): θερμοκρασία και παρατήρηση
  receiptTempC   Float? // °C κατά την παραλαβή (ευπαθή/ψυγόμενα)
  receiptIssue   String? // π.χ. «σχισμένη συσκευασία»· κενό = χωρίς πρόβλημα
  supplierItemId String? // μετά την αντιστοίχιση
  tradeItemId    String? // μετά την αντιστοίχιση
  genericItemId  String? // τελικό: πού «πέφτει» το απόθεμα

  @@index([orgId, documentId])
}
```

## 10. Απόθεμα, σπάσιμο συσκευασίας και συνταγές (επόμενο βήμα, όχι τώρα)

- `StockMovement` αποκτά `genericItemId` — ο πίνακας ήδη είναι append-only με τελικό `warehouseId`, οπότε η προσθήκη είναι καθαρή.

### Σπάσιμο: από τη συσκευασία αγοράς στη μονάδα χρήσης της συνταγής

Η αλυσίδα μετατροπής είναι ήδη πλήρης στα μοντέλα και τρέχει **αυτόματα κατά την παραλαβή**:

```
ποσότητα παραστατικού × packQty (SupplierItem) × contentQty (TradeItem) → βασική μονάδα (GenericItem)
```

Παράδειγμα: τιμολόγιο «2 κιβώτια» → `packQty = 12` → 24 τεμάχια 1L → `contentQty` → **24.000 ml** είσοδος
στο γενικό είδος «Γάλα αγελάδος». Η συνταγή καταναλώνει πάντα σε βασική μονάδα (ml/g/τεμ),
οπότε δεν χρειάζεται καμία επιπλέον ενέργεια για να «φανεί» το υλικό στη συνταγή.

Σχεδιαστικές αποφάσεις:

- **Το απόθεμα τηρείται σε ένα επίπεδο** — τη βασική μονάδα κατανάλωσης. Δεν κρατάμε ξεχωριστό απόθεμα
  «κλειστών κιβωτίων»: η οθόνη αποθέματος **εκφράζει** το απόθεμα και σε συσκευασίες
  («≈ 2 κιβώτια + 4 λίτρα», από `contentQty`), χωρίς δεύτερο πίνακα αποθέματος.
- **Σπάσιμο: αυτόματο + διόρθωση από τον χρήστη.** Η μετατροπή της αλυσίδας γίνεται αυτόματα στην
  παραλαβή· επιπλέον ο χρήστης μπορεί πάντα να καταχωρεί **διόρθωση αποθέματος** (χειροκίνητη κίνηση
  ± σε βασική μονάδα, με αιτιολογία, π.χ. «σπασίματα», «μέτρηση απογραφής», «άνοιγμα συσκευασίας»).
  Οι διορθώσεις είναι κανονικά `StockMovement` (append-only) με πηγή «manual» — πλήρες ιστορικό,
  τίποτα δεν παρακάμπτεται.
- **Χύμα είδη** (σακί αλεύρι 25 kg → γραμμάρια στη συνταγή): ίδια αλυσίδα — το ιδιωτικό `TradeItem`
  «Αλεύρι χύμα 25 kg» έχει `contentQty = 25_000_000 mg`, `packQty = 1`, και το σπάσιμο είναι αυτόματο.

### Ιχνηλασιμότητα: παρτίδες και ημερομηνίες λήξης (από την πρώτη υλοποίηση)

Νομοθετικό πλαίσιο που δεσμεύει τη σχεδίαση:

- **Καν. (ΕΚ) 178/2002, άρθρο 18** (Γενικός Κανονισμός Τροφίμων): «ένα βήμα πίσω, ένα βήμα μπροστά» —
  κάθε επιχείρηση πρέπει να αναγνωρίζει ποιος της προμήθευσε κάθε τρόφιμο και σε ποιες επιχειρήσεις
  πούλησε η ίδια, με στοιχεία διαθέσιμα στις αρχές κατ' απαίτηση. Το άρθρο 19 επιβάλλει ανάκληση/απόσυρση.
  Ο κανονισμός δεν επιβάλλει ρητά *εσωτερική* ιχνηλασιμότητα (ποια παρτίδα μπήκε σε ποια παραγωγή),
  αλλά η Κομισιόν τη συνιστά — χωρίς αυτήν η ανάκληση γίνεται «όλη η παραγωγή της ημέρας».
- **Εκτελ. Καν. (ΕΕ) 931/2011**: αυστηρότερα για τρόφιμα ζωικής προέλευσης (γάλα!) — παρτίδα, ποσότητα,
  ημερομηνία αποστολής, αποστολέας/παραλήπτης συνοδεύουν κάθε παρτίδα.
- **Καν. (ΕΚ) 852/2004, άρθρο 5**: υποχρεωτικό σύστημα HACCP σε κάθε επιχείρηση τροφίμων —
  η παραλαβή πρώτων υλών (έλεγχος θερμοκρασίας, ακεραιότητας συσκευασίας, λήξης, εγκεκριμένοι
  προμηθευτές) και η FIFO/FEFO ροή αποθεμάτων είναι τυπικά σημεία ελέγχου του ΕΦΕΤ.
- **Καν. (ΕΕ) 1169/2011**: πληροφόρηση καταναλωτή, Παράρτημα II (14 αλλεργιογόνα) — σχετικό για τις
  συνταγές: τα αλλεργιογόνα κληρονομούνται από τα γενικά είδη (μελλοντικό πεδίο στο `GenericItem`).
- **ΕΦΕΤ**: η αρχή ελέγχου· οι οδηγοί της (π.χ. «Γενικός Οδηγός HACCP για γαλακτοκομικά») απαιτούν
  αναγνώριση κάθε παρτίδας με ημερομηνία παραγωγής/λήξης και ιχνηλασιμότητα πρώτων υλών.
  Κυρώσεις: Ν.4235/2014.
- **Περίοδος διατήρησης**: ο 178/2002 δεν ορίζει ρητή· η καθοδήγηση της Κομισιόν προτείνει 5 έτη
  (μικρότερη για ευπαθή). Σχεδιαστικά: τα δεδομένα παρτίδων/κινήσεων δεν διαγράφονται ποτέ
  (append-only), οπότε η απαίτηση καλύπτεται δομικά.

Πώς απαντά η σχεδίαση: «ένα βήμα πίσω» = `StockLot` → τιμολόγιο αγοράς → προμηθευτής ✓·
«ένα βήμα μπροστά» για B2B = `FiscalDocument`/`partyId` ✓ (λιανική σε τελικό καταναλωτή εξαιρείται
νομίμως)· εσωτερική ιχνηλασιμότητα = κίνηση κατανάλωσης συνταγής με `lotId` (φάση συνταγών)·
έλεγχοι παραλαβής HACCP = πεδία στη `PurchaseLine` (παρακάτω).

Κάθε παραλαβή με batch/λήξη (από GS1 σάρωση, myDATA ή χειροκίνητα) δημιουργεί/βρίσκει παρτίδα,
και οι κινήσεις αναφέρονται σε αυτήν:

```prisma
// Παρτίδα γενικού είδους σε αποθήκη: από πού ήρθε, πότε λήγει.
model StockLot {
  id            String    @id @default(cuid())
  orgId         String
  genericItemId String
  warehouseId   String
  batchNumber   String? // AI(10) ή χειροκίνητη
  expiresAt     DateTime? // AI(17)
  documentId    String? // το τιμολόγιο αγοράς που την έφερε
  createdAt     DateTime  @default(now())

  @@unique([orgId, genericItemId, warehouseId, batchNumber])
  @@index([orgId, expiresAt])
}
```

- Το `StockMovement` αποκτά `lotId String?` (κενό για είδη χωρίς παρτίδες, π.χ. χύμα από δεξαμενή).
- **FEFO** (First-Expired-First-Out): η κατανάλωση από συνταγή και η οθόνη αποθέματος προτείνουν
  την παρτίδα με την πιο κοντινή λήξη· η αναφορά «λήγουν σε N ημέρες» βγαίνει από το `expiresAt`.
- Ανάκληση/έλεγχος: «τι ήρθε με την παρτίδα X και πού πήγε» είναι απλό query στα movements της.
- Οι διορθώσεις χρήστη (παραπάνω) μπορούν να αφορούν συγκεκριμένη παρτίδα (π.χ. «έληξε, πετάχτηκε»).

### Συνταγές

- Η συνταγή (`Recipe`) θα αναφέρεται σε `GenericItem` + ποσότητα σε βασική μονάδα· το κόστος της βγαίνει
  από την τρέχουσα τιμή του επιλεγμένου `SupplierItem` (§7) διαιρεμένη με `contentQty`.
- Αυτά καταγράφονται εδώ για να μη σχεδιαστούν τα παραπάνω με τρόπο που τα κλείνει έξω· δεν υλοποιούνται σε αυτό το κύμα.

## 16. Φάση 5: συνταγές και παραγωγή (σε εξέλιξη)
